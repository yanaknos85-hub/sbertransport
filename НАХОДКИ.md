## В1. Кто собирает грузовой маршрут из заявок

**Ответ:** маршруты собирает отдельный сервис **route-cargo**, его в папке нет. На это указывают три независимых признака: (1) id поездки в trips-cargo совпадает с id маршрутного листа в схеме `route_cargo`; (2) интерфейс планировщика (corp-cargo, модуль Planner) весь работает через REST-префикс `route-cargo`, в том числе кнопка «Автопланирование» → `POST /route-cargo/srm/start`; (3) типы создания маршрута во фронте — «Автоматически (шедулер)», «Ручной», «Интеграция», «Автопланирование SRM». Сам шедулер (класс, cron) увидеть нельзя, пока не скачан route-cargo.
**Статус:** частично (сервис определён, код шедулера не просмотрен).

## В2. Какой вход использовать для рейсов: Kafka или REST

**Ответ:** для внешней системы (наш сервис планирования) пригоден только REST `POST /integration` — это единственный вход, рассчитанный на интеграцию (есть прокси для внешнего контура, авторизация по JWT контрагента или интеграционного клиента). Но REST **теряет большую часть данных**: заявки (`Trip.requests`) не заполняются, пропадают `contractorTripId`, `workgroup`, `contragentInn`, `reestr`, `hourTariff`, `desiredAuto`, `source`, тип точки; время окончания не заполняется; изменить созданную поездку через REST нельзя. Kafka-вход `service.request.cargo.routes` умеет и создавать, и обновлять, и отменять поездку, но это внутренний контракт route-cargo (формат `RouteMessage` из библиотеки `request-cargo-messaging`, которой нет в папке), и настройки доступа к топикам в коде не хранятся.
**Статус:** частично (REST разобран полностью; ACL Kafka по коду не определить).

## В4. Изменение поездки после создания

**Ответ:** в trips-cargo есть `PATCH /contractor/{contractorId}/trip/{tripId}/`, но он открыт только диспетчеру и водителю контрагента и меняет только исполнение (водитель, статус, плановая смена, фактические данные, время подачи для диспетчера, грузчики, QR). ## В5. Автоотмена ночью для заявок без времени

**Ответ:** гипотеза подтверждается. Шедулер trips-cargo раз в минуту берёт поездки в статусе `WAITING_FOR_ASSIGNMENT` без водителя и без плановой смены у контрагентов с `autoassign = true`; ищет водителя, когда до начала осталось меньше 30 минут, и за 10 минут до начала переводит поездку в `ORDER_CANCELLED_BY_DRIVER`. Начало поездки = минимальная желаемая дата заявок в часовом поясе заявки, поэтому заявка «19.09 00:00» (МСК) ищет водителя с 23:30 и отменяется в 23:50 18.09. Отключить можно тремя способами: флаг `autoassign` у контрагента (PATCH в dispatcher), cron шедулера, либо отрицательное `driver.assign.finishSearchMin` (отмена сдвигается после начала). Окна настраиваются свойствами. Важная находка: **поездки, созданные через REST `/integration`, в автоназначение не попадают вообще** — у них пустой список заявок.
**Статус:** закрыт.

**Доказательства:**
- Триггер: `trips-cargo-main/trips-cargo-main/application/src/main/java/ru/sber/transport/trips/cargo/scheduler/DriverAssigningProcessor.java`, строка 20: «`@Scheduled(cron = "${driver.assigning.cron:0 * * * * *}")`» — каждую минуту. То есть поездка, на которую диспетчер заранее запланировал смену (`planningShiftId`), из автоназначения и автоотмены исключается.

## В6. Проверка входа и координаты

**Ответ:** на входе `POST /integration` обязательные поля **не проверяются нигде** — ни аннотациями, ни `@Valid`/`@Validated`, ни вручную. Проверка одна — дубль номера маршрута. ## В7. Подбор машины

**Ответ:** платформа машину под груз **не подбирает**. `desiredAuto` (вес, объём) из REST отбрасывается (см. ## В8. Учётная запись водителя

**Ответ:** отдельной операции «переназначить учётную запись (рабочее место) на другого человека» в коде нет — исполнитель прав. - Маршрут: `…/messaging/listeners/ListenerConfig.java`, строки 355–357: «`Consumer<Message<RouteMessage>> routeInput(RouteProcessor service) { return message -> service.handle(message.getPayload()); }`»; `…/messaging/processors/RouteProcessor.java`: «`service.save(mapper.messageToEntity(message));`» (лог «Редактирование маршрута»); `…/service/impl/RouteServiceImpl.java`: «`return repository.save(routelist);`». `RouteMessage` — из `ru.sberbank.ditsib.transport.route.messaging` (артефакт `ru.sber.transport.cargo:route-cargo-messaging:250414-1`, `application/pom.xml`, строки 215–217).
- Состав маршрутного листа: `…/database/model/Routelist.java` и `init.sql`, строки 245–257: `id, humanreadableid (UNIQUE, updatable = false), tariff_id, contractor_info jsonb, status, status_code, cost, distance, active`. Точек, водителя, машины, времени в маршрутном листе нет.
- Связь с заявками: `…/database/model/Request.java`, строки 360–366: «`@OneToOne … @JoinColumn(name = "trip_id", insertable = false, updatable = false) private Routelist routelist;`» — заявка ссылается на маршрут через `trip_id`; значит, id маршрута = id поездки в trips-cargo = `trip_id` заявки (согласуется с В1). Водитель и машина хранятся «отпечатком» в самой заявке: `init.sql`, таблица `request`: «`driver jsonb` — Отпечаток водителя», «`vehicle jsonb` — Отпечаток автомобиля».
- REST: `…/controller/OtoEngineerController.java`: «`POST cargo/`» — «Получить детальную информацию по заявкам по грузоперевозкам для инженера ОТО», «`GET cargo/{organizationId}/template`» — шаблоны регулярной перевозки (с `cron_expression`, `…/mappers/TemplateMapper.java`, строки 82–94).

**Для требований:** OTO — источник для отчётности и контроля инженером ОТО, а не точка интеграции. Писать в него нельзя; данные о наших рейсах туда попадут автоматически, только если маршрут пройдёт через route-cargo (топик `service.route.cargo`) и заявки — через request-cargo. Рейсы, созданные напрямую через REST `/integration` trips-cargo, в OTO не появятся: OTO не слушает ни `service.trip`, ни `service.contractor.update.trip`, а trips-cargo не пишет в топики, которые слушает OTO (см. карту топиков в начале файла).

**Не ясно:**
- что именно публикует route-cargo в `service.route.cargo` при изменении маршрута (все поля или только статус) — нужен код route-cargo;
- откуда OTO берёт стоимость фактического рейса — из заявок (`service.request.cargo*`) или из маршрута.
