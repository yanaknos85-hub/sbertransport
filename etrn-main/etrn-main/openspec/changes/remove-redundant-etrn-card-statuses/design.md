## Context

Enum `EtrnCardStatus` (8 значений) и allowlist force-transition в `EtrnServiceImpl` содержат `ERROR` и `OUTCOME_UNKNOWN` — статусы, которые не используются бизнес-процессом карточки. Показатели уровня ошибок/неопределённости существуют на уровне операции подписания (`SigningOperationStatus`), который остаётся без изменений.

Факты, влияющие на решение:
- Колонка `etrn_cargo.etrn.status` — `VARCHAR(64) NOT NULL` **без CHECK-констрейнта**; сущность `Etrn` хранит статус как `String` — валидации на уровне БД/JPA нет.
- `forceTransition` — единственный код, ссылающийся на `EtrnCardStatus.ERROR` / `EtrnCardStatus.OUTCOME_UNKNOWN` в `main`.
- Тесты `EtrnServiceImplTest` (`forceTransition_errorStatus_allowed`, `forceTransition_outcomeUnknown_allowed`) и константы `TestCommon.STATUS_ERROR` / `STATUS_OUTCOME_UNKNOWN` — единственные ссылки в `test`.
- Фронтенд уже работает с 6 статусами (целевой `EtrnStatusNames` содержит ровно их).
- `GIGACODE.md` §6.1 уже описывает 6 статусов карточки — документ был «впереди» кода; SSOT-доки в `_documents/knowledge` частично противоречат коду.

## Goals / Non-Goals

**Goals:**
- Ровно 6 статусов в `EtrnCardStatus`, соответствующих целевой модели (TS-фронтенд, `GIGACODE.md`).
- Allowlist force-transition = `WAIT_CONDITIONS`, `WAIT_KORUS_CONFIRMATION`.
- Код и тесты компилируются, тесты зелёные, спецификации и SSOT-доки синхронизированы.

**Non-Goals:**
- Не трогаем `SigningOperationStatus` (уровень операции подписания) и `EtrnTitleStatus`.
- Не вводим CHECK-констрейнт по статусу в БД (отдельная тема целостности).
- Не меняем HTTP-статусы/DTO-контракт `force-transition`.
- Не реализовываем reconciliation-механику — она закрывалась удалёнными статусами и более не нужна на уровне карточки.

## Decisions

1. **Физическое удаление значений enum, а не деградирующее помечание (`@Deprecated`).**
   - Обоснование: сервис версии 1.0, статусы не использовались процессом; `@Deprecated` оставил бы «мёртвые» значения, которые continue to leak в Swagger (record + `@Schema` на enum) и в фильтры списка (`statusFilter` — свободная строка).
   - Альтернатива (soft-deprecation) отклонена: не даёт пользы без реальных внешних потребителей этих значений.
2. **Без DB-миграции.**
   - Обоснование: нет CHECK-констрейнта, JPA-поле — `String`, `ddl-auto: validate` не страдает. Колонка остаётся `VARCHAR(64)` и принимает любые 6 новых значений.
   - Альтернатива (миграция с ограничением домена) отклонена как расширение scope; при необходимости выносится отдельным изменением.
3. **Остаточные строки со статусами `ERROR`/`OUTCOME_UNKNOWN` в БД не мигрируются автоматически.**
   - Обоснование: такие строки, по определению процесса, не создаются; если они появятся (отладочные данные) — это данные, а не схема. Преддеплоемная проверка `SELECT status, count(*) FROM etrn_cargo.etrn GROUP BY status` + ручное согласование единичных записей через существующий механизм.
   - Поведение API к таким строкам: `forceTransition` отклоняется (`InvalidTransitionException`), чтение/список работает (статус — строка).
4. **Дополнительный сценарий спека** «Переход из удалённого статуса» фиксирует контракт для остаточных данных.
5. **Документация обновляется в рамках изменения** (обязательство `GIGACODE.md` §13): `_documents/knowledge/init/knowledge/data-model.md`, `05-state-model.md`, устаревшая строка OUT-OF-SCOPE в `openspec/specs/etrn-korus/spec.md`.

## Risks / Trade-offs

- [Остаточные строки `ERROR`/`OUTCOME_UNKNOWN` в проде] → преддеплоемный count по статусам; при нахождении — ручное согласование до релиза; API к ним деградирует корректно (read + отказ force-transition).
- [Несогласованный деплой бэкенд/фронтенд] → фронтенд уже на 6 статусах (целевой маппинг задан); даже при реверсивном порядке бэкенд не ломает фронтенд (лишние значения просто не возвращаются).
- [Потеря reconciliation-возможности для «зависших» карточек] → намеренный trade-off: reconciliation на уровне карточки не нужен, ошибки подписания видны по `SigningOperationStatus`; ручное восстановление остаётся доступно административными средствами БД при необходимости.
- [Устаревшие ссылки на 8 статусов в знаниях/архивах] → архивные изменения OpenSpec не редактируются; текущие спеки и SSOT-доки синхронизируются в рамках изменения.

## Migration Plan

1. Преддеплой: `SELECT status, count(*) ... GROUP BY status` — убедиться, что `ERROR`/`OUTCOME_UNKNOWN` = 0 (или согласовать вручную).
2. Деплой бэкенда (schema-изменений нет).
3. Откат: переразвёртывание предыдущей версии артефакта — обратно совместимо (старый код читает те же 6 статусов).
